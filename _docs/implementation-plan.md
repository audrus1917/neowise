# План выполнения задания Neowise

## Цель и границы

Менеджер вводит заявку и получает тему и черновик ответа. При сбое AI приложение предлагает обработать заявку вручную и убирает устаревший результат. Отправку клиенту менеджер выполняет самостоятельно.

Этот документ фиксирует план реализации требований из `README.md` и критерии проверки. Описанная ниже реализация добавлена в код. Фактические команды запуска и тестирования приведены в `README.md`.

Сохраняем текущую архитектуру: Node.js 20+, встроенный HTTP-сервер, HTML со встроенным JavaScript и выданный имитатор модели. Зависимости, внешний AI и ключи не нужны. `mock-ai.mjs` оставляем без изменений.

## Окружение Docker Compose

Добавлено окружение для запуска исходного приложения: `Dockerfile` на базе Node.js 22 Alpine и `compose.yaml` с одним сервисом `app`. Контейнер работает от пользователя `node`, слушает `0.0.0.0:3000` и публикует порт только на `127.0.0.1` хоста. При прямом запуске через Node.js сохраняется адрес `127.0.0.1`; переопределить его можно переменной `HOST`.

Запуск: `docker compose up --build -d`. Остановка: `docker compose down`. Для другого порта хоста: `PORT=3001 docker compose up --build -d`. После изменений исходников образ нужно пересобирать.

Образ содержит приложение и каталог `test`, включённый в `COPY` в `Dockerfile` и список разрешений в `.dockerignore`. После сборки тесты запускаются через `docker compose run --rm --no-deps app node --test test/triage.test.mjs`.

## 1. Проверить входные данные

В `server.mjs` отделить чтение и разбор входного JSON от обращения к модели. Битый JSON должен приводить к HTTP 400, а не попадать в обработку ошибок модели.

После разбора проверить, что тело — JSON-объект, а `text` — строка, содержащая хотя бы один непробельный символ. Значения `null`, массивы, отсутствующий `text`, числа, пустая строка и строка из пробелов должны возвращать HTTP 400 с телом:

```json
{"status":"invalid_input"}
```

Для некорректного ввода модель не вызывается. Проверка через `trim()` не требует изменять исходный текст, передаваемый имитатору.

## 2. Ограничить время ожидания модели

Ограничить вызов `classify` временем 300 мс. Передать имитатору `AbortSignal`, который он уже поддерживает. Для явного ограничения ожидания можно использовать `Promise.race` между вызовом модели и таймером: при истечении срока прервать вызов через `AbortController` и перейти к ручной обработке. Таймер обязательно очищать в `finally`, включая успешный ответ и ошибку до истечения срока.

Не изменять задержки и сценарии внутри `mock-ai.mjs`. Позднее завершение вызова не должно приводить к повторной отправке HTTP-ответа или необработанному отклонению промиса.

## 3. Проверить ответ модели

Считать результат AI недоверенными данными. В отдельном участке обработки разобрать JSON и проверить:

- Результат — объект, а не `null` или массив.
- `topic` строго равен `delivery`, `pricing` или `other`.
- `draft` — строка, содержащая хотя бы один непробельный символ.

Только после проверки вернуть HTTP 200:

```json
{"status":"ready","topic":"delivery","draft":"Спасибо за обращение. Уточним детали заявки."}
```

Собрать ответ из явно выбранных полей; не переносить произвольные поля модели через spread. Ошибку вызова, таймаут, битый JSON модели и неподходящую структуру обработать одинаково: HTTP 200 с телом:

```json
{"status":"manual_review","topic":null,"draft":null}
```

Обработка сбоев модели должна охватывать только вызов модели, разбор и проверку её результата. Непредвиденные серверные ошибки не следует маскировать под штатную ручную обработку.

## 4. Обновить страницу

В `index.html` показывать понятные менеджеру тему и черновик вместо сырого JSON. При `manual_review` очищать предыдущую тему и черновик и выводить сообщение, например: «Не удалось подготовить ответ автоматически. Обработайте заявку вручную».

При неверном вводе предложить ввести текст заявки. При сетевой ошибке показать сообщение о невозможности получить результат. Очищать устаревший результат при новой отправке; на время запроса блокировать повторную отправку и восстанавливать кнопку в `finally`, чтобы ответы параллельных запросов не перезаписывали друг друга.

Для текста заявки и ответа модели использовать `textContent`, чтобы содержимое не интерпретировалось как HTML. Сохранить доступное уведомление о результате через `aria-live`.

## 5. Добавить исполнимые проверки

Использовать встроенные `node:test` и `node:assert/strict`, без установки библиотек. В реализации HTTP-тесты создают сервер через `createApp`, запускают его на автоматически назначаемом порту и закрывают сервер и соединения после проверок. Отдельный процесс не требуется; обычный запуск через `node server.mjs` сохраняется.

Проверить следующие сценарии через `POST /api/triage`:

| Сценарий | Ожидаемый результат |
| --- | --- |
| Обычная заявка | HTTP 200, `ready`, допустимая тема, непустой черновик |
| Битый JSON; тело `null`, массив или примитив; отсутствующий, нестроковый, пустой или пробельный `text` | HTTP 400, `invalid_input` |
| `[error]` | HTTP 200, `manual_review`, `topic` и `draft` равны `null` |
| `[timeout]` | Тот же результат без ожидания полной задержки имитатора в 1200 мс |
| `[bad-json]`, `[bad-topic]`, `[empty-draft]` | HTTP 200, `manual_review`, поля равны `null` |

Проверка таймаута должна учитывать накладные расходы HTTP и планировщика, но отличать ограничение 300 мс от полной задержки имитатора. Не требовать завершения HTTP-запроса ровно за 300 мс.

Для файла тестов `test/triage.test.mjs` команда запуска:

```sh
node --test test/triage.test.mjs
```

Файл тестов создан; команда запускает проверки через встроенный тестовый раннер Node.js.

В браузере отдельно проверить последовательность: успешная заявка → заявка с каждой меткой сбоя. Предыдущий черновик должен исчезать. Также проверить неверный ввод, недоступность сервера и восстановление кнопки после завершения запроса.

## 6. Подготовить результат к сдаче

После реализации добавить в `README.md` фактическую команду запуска тестов. Просмотреть итоговый diff и выполнить сфокусированные проверки.

В описании PR указать место проверки ответа AI, поведение при сбоях, использованный AI и самостоятельно выполненные проверки. Отдельно отметить незавершённые части, если они есть. Коммиты, публикацию ветки и открытие PR выполнять только по явному запросу пользователя; требования задания к сдаче сами по себе не являются командой выполнить эти действия сейчас.

Польза для менеджера: меньше времени на подготовку первого ответа; измерять её можно по среднему времени от открытия заявки до готового, проверенного менеджером черновика.

## CI/CD для GitHub

В `.github/workflows/ci.yml` добавлена последовательность проверок: HTTP-тесты на Node.js 20/22/24 → проверка Compose, сборка и тесты Docker → проверка HTTP через опубликованный порт контейнера.

Для CD принят вариант доставки образа в GHCR. После успешных проверок в `main` образ передаётся через временный артефакт в отдельную задачу публикации. Она использует `GITHUB_TOKEN` и публикует теги `sha-<полный SHA коммита>` и `latest`. Повторная сборка перед публикацией не нужна: публикуется проверенный образ. Ветки разработки и PR выполняют проверки без публикации; право `packages: write` есть только у задачи публикации.

HTTP-проверка в `scripts/smoke.mjs` запускается отдельно от тестового сервера: она проверяет уже работающий контейнер, включая адрес прослушивания и проброс порта. Локально можно вызвать `node scripts/smoke.mjs`, передав при необходимости другой URL первым аргументом.

Развёртывание на сервер не настроено: место размещения приложения пока не задано. Удалённый запуск CI в `dev` проверен. Публикация в GHCR запускается после успешных проверок в `main` и до слияния PR остаётся непроверенной.
